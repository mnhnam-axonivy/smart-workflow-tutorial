# PIIマスキングガードレール

**PIIマスキングガードレール**は、ユーザーメッセージ内の個人識別情報（PII）をLLMに届く前に自動検出し、機密値を不透明なプレースホルダートークンに置き換え、モデルの応答で元の値を復元します — 実際の個人データをサードパーティのAIサービスに渡しません。

[入力ガードレール]や[出力ガードレール]と異なり、`PiiMaskingGuardrail`はリクエストをブロックしません。**ステートフルで透過的な**ガードレールです：ユーザーは元の値が復元された自然な応答を受け取り、LLMは匿名化されたプレースホルダーのみを処理します。

---

> **[入力ガードレール]の知識が必要です。** このフィーチャーに取り組む前に、`AgenticProcessCall`要素へのガードレールの追加に慣れておいてください。
>
> **このガイドの例：** 7種類のPIIを含むメッセージを1つのプロセスでカスタマーサポートエージェントに送信します — すべての値はLLM呼び出し前に匿名化され、出力で復元されます。
>
> 完成したプロセスは `tutorial/processes/tutorial/features/Feature11.p.json` にあります。

---

## 始める前に

GDPRやCCPAなどのプライバシー規制は、個人データをサードパーティのプロセッサーに送信することを制限しています。`PiiMaskingGuardrail`を使用すると、実際のPIIを公開せずにクラウドLLMプロバイダーにユーザーメッセージを転送できます — LLMはプレースホルダートークンのみを参照し、レスポンスはユーザーに届く前に自動的に復元されます。

---

## 仕組み

`PiiMaskingGuardrail`は`SmartWorkflowInputGuardrail`と`SmartWorkflowOutputGuardrail`の**両方**を実装しています。正しく機能させるには、エージェントの**入力ガードレール**と**出力ガードレール**の両方に登録する必要があります。

**入力時：** ガードレールはメッセージをPIIパターンでスキャンし、各値を`<TYPE_hash>`形式の決定論的トークン（例：`<EMAIL_a1b2c3d4e5f6>`）に置き換え、呼び出しIDをキーとしてマッピングを保存します。

**出力時：** ガードレールは保存されたマッピングを使用して、すべてのプレースホルダーを元の値に置き換えます。

検出されるPIIの種類：

| 種類 | 例 |
| --- | --- |
| メール | `john.doe@example.com` |
| 電話番号 | `+1-555-123-4567` |
| クレジット/デビットカード番号 | `4532015112830366` |
| SSN（社会保障番号） | `123-45-6789` |
| 生年月日 | `15/06/1990` |
| IPアドレス | `192.168.1.42` |
| MACアドレス | `00:1A:2B:3C:4D:5E` |

> クレジットカード番号は**Luhnアルゴリズム**で検証されます — チェックサムを満たさないランダムな数字列はマスクされません。

---

## なぜ使うのか？

- **GDPRやCCPAへの準拠** — 個人データがインフラ境界の外に出ることがない
- **データ主権** — 顧客データを自社の管理下に置く
- **ユーザーへの透過性** — 最終的な応答で元の値が復元される
- **コード不要** — Java実装が不要
- **すべてのクラウドプロバイダーに対応** — LLMは匿名化されたテキストのみを処理

---

## ステップ1 — 両方のリストにPiiMaskingGuardrailを追加する

`AgenticProcessCall`の設定で、**入力ガードレール**と**出力ガードレール**の両方を設定します：

| フィールド | 値 |
| --- | --- |
| 入力ガードレール | `["PiiMaskingGuardrail"]` |
| 出力ガードレール | `["PiiMaskingGuardrail"]` |

> 入力のみに設定すると、`<TYPE_hash>`プレースホルダーが最終的なユーザー応答に表示されます。必ず両方に登録してください。

---

## ステップ2 — システムプロンプトを設定する

このステップは任意ですが、省略すると出力の復元がエラーなく失敗する場合があります。

出力ガードレールは、モデルの応答を走査して挿入した`<TYPE_hash>`トークンを探し、元の値に置き換えます。LLMがトークンを言い換えた場合（例：`<EMAIL_a1b2c3d4e5f6>`を"メールアドレス"と記述）、トークンが見つからず元の値は**復元されません** — エラーは発生せず、プレースホルダーが欠落したままになります。

システムプロンプトを追加することでこのリスクを軽減できます：

```text
Values formatted as <TYPE_hash> are anonymized placeholders — the original sensitive data was removed before reaching you. Treat each placeholder as an opaque token and echo it back as-is.
```

## 例

![プロセス例](cms:/Files/Images/feature11-00)

### モックデータ

7種類のPIIを含むメッセージ：

```java
in.query = "Please echo back all fields: MAC 00:1A:2B:3C:4D:5E, email john.doe@example.com, " +
           "phone +1-555-123-4567, card 4532015112830366, SSN 123-45-6789, " +
           "born 15/06/1990, IP 192.168.1.42.";
```

> 上記のデータは完全に架空のものであり、実在の人物、アカウント、またはシステムとは一切関係ありません。

### エージェントの設定

| フィールド | 値 |
| --- | --- |
| システムプロンプト | `Values formatted as <TYPE_hash> are anonymized placeholders...` |
| 入力ガードレール | `["PiiMaskingGuardrail"]` |
| 出力ガードレール | `["PiiMaskingGuardrail"]` |

### LLMが受け取る内容

メッセージがモデルに届く前に、すべてのPII値がトークンに置き換えられます：

```text
Please echo back all fields: MAC <MAC_ADDRESS_3c4d5e01a2b3>, email <EMAIL_a1b2c3d4e5f6>,
phone <PHONE_55512345678a>, card <CREDIT_DEBIT_CARD_NUMBER_11283036>, SSN <SSN_456789abc123>,
born <DATE_OF_BIRTH_06199042de56>, IP <IP_ADDRESS_168001042bcd>.
```

### 結果

LLMがプレースホルダーを使用して応答した後、ガードレールが元の値を復元します：

```text
MAC: 00:1A:2B:3C:4D:5E
Email: john.doe@example.com
Phone: +1-555-123-4567
Card: 4532015112830366
SSN: 123-45-6789
Born: 15/06/1990
IP: 192.168.1.42
```

## 設定リファレンス

| 変数 | 説明 | デフォルト |
| --- | --- | --- |
| `AI.Guardrails.DefaultInput` | `PiiMaskingGuardrail`をすべてのエージェントにグローバルに適用します。 | *(なし)* |
| `AI.Guardrails.DefaultOutput` | `PiiMaskingGuardrail`をすべてのエージェントにグローバルに適用します。 | *(なし)* |

`variables.yaml`でグローバルに有効化するには：

```yaml
Variables:
  AI:
    Guardrails:
      DefaultInput:  "PiiMaskingGuardrail"
      DefaultOutput: "PiiMaskingGuardrail"
```

---

## よくある間違い

- **入力のみに登録する** — プレースホルダーが実際の値の代わりに応答に表示されます。必ず入力と出力の両方に追加してください。
- **LLMがプレースホルダーを変更する** — 一部のモデルが`<EMAIL_a1b2c3d4e5f6>`を"メールアドレス"と言い換え、復元が壊れます。システムプロンプトのヒントを追加し、使用するモデルでテストしてください。
- **これを完全なプライバシーソリューションとして扱う** — PIIマスキングはリスクを軽減しますが、完全なプライバシー保証ではありません。メタデータ、セッションID、文脈的な手がかりによって個人を特定できる場合があります。データ最小化とプライバシー・バイ・デザインの原則と組み合わせてください。
