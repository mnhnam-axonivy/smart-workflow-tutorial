# RAGとは？

**検索拡張生成（RAG：Retrieval-Augmented Generation）**は、AIが自社のドキュメントを使って質問に答えられるようにする技術です。学習データだけに頼るのではなく、AIはまずナレッジベースから関連情報を検索し、その情報をもとに回答を生成します。

---

## 解決する課題

LLMは学習データしか知りません。社内ドキュメント、製品カタログ、社内規定、学習カットオフ以降に書かれた内容については一切知識を持ちません。全てのドキュメントをプロンプトに貼り付けることもできますが、コストが高くなり、処理が遅くなり、コンテキストウィンドウの上限に達してしまいます。

会話中にドキュメントを共有しても、モデルはそれを永続的に学習するわけではありません。RAGがなければ、新しい会話のたびに組織のドキュメントに関する知識がゼロからスタートします。

## 身近な例：図書館司書

図書館に入って、こう尋ねます：*「ローマ帝国はなぜ滅亡したのですか？」*

熟練した司書は記憶だけで答えません：

1. まず、関連する本を図書カタログで検索します。
2. 次に、ローマの建築や日常生活に関する内容を除いた、最も関連性の高い章だけを取り出します。
3. そして、それらのページをざっと読みます。
4. 最後に、こう説明します：「歴史家たちは一般的に、ローマ帝国の滅亡は政治的不安定、経済的衰退、蛮族の侵攻による軍事的圧力、内部腐敗の組み合わせによるものだと見ています。」

これがまさにRAGの仕組みです：

| 図書館司書 | RAGシステム |
| --- | --- |
| あなたの質問 | ユーザーのクエリ |
| カタログで検索する | ベクトルストアへのセマンティック検索 |
| 関連する章を取り出す | 取得されたドキュメントチャンク |
| そのページを読む | LLMプロンプトに注入されたチャンク |
| 自分の言葉で説明する | LLMがグラウンドされた回答を生成 |

司書は全ての本を暗記しているわけではありません — 必要な情報をすばやく見つける方法を知っているのです。RAGはLLMに同じ能力を与えます。

## 仕組み — 基本的なフロー

RAGは完全なキーワード一致ではなく、意味による検索を行います — これを**セマンティック検索**と呼びます。これを実現するために、ドキュメントと質問の両方が**埋め込み（エンベディング）**と呼ばれる数値表現に変換されます。意味が似ていれば、使われている単語が異なっていても、数学的に近い埋め込みが生成されます。

大まかに言うと、全てのRAGのやり取りは3つのステップを経ます：

1. ユーザーの質問が埋め込みに変換される
2. ベクトルストアが最も類似した埋め込みを持つドキュメントチャンクを見つける
3. そのチャンクがプロンプトに追加され、LLMがそれを根拠とした回答を生成する

> **重要：** RAGはLLMを再学習またはファインチューニングするわけではありません。モデル自体は変更されません — 各質問に対して追加のコンテキストが提供されるだけです。

## RAGパイプライン

RAGには2つの部分があります：

- **インジェスション（取り込み）** — ドキュメントを検索可能な形に準備します。ドキュメントが変更されたときに実行します。
- **リトリーバル（検索・取得）** — ユーザーが質問するたびにドキュメントを検索します。クエリごとに実行します。

---

### パート1: インジェスション（取り込み）

*ドキュメントが変更されたとき、または一度だけ実行されます。ナレッジベースを準備します。*

ソースドキュメントは処理・保存され、後で検索できるようになります。出力は取得に対応したベクトルストアのインデックスです。

![インジェスションパイプライン](cms:/Files/Images/appendix01-ingestion)

#### ステップ1: データソース

エージェントに知らせたい生のドキュメントを収集します。様々なフォーマットや場所から取り込むことができます。

例：PDF形式の従業員ハンドブック、Markdownのナレッジベース記事、CSVの製品リスト、Word形式の規定文書、Webページ、データベースのエクスポートなど。ソースドキュメントが整理されていて構造化されているほど、検索品質は高くなります。

#### ステップ2: 読み込み（Load）

各ソースファイルから生のテキストコンテンツを抽出します。このステップでは、フォーマット、レイアウト、バイナリエンコーディングを取り除き、読み取り可能なテキストだけを残します。

例：PDF形式の請求書を解析して `"Item: Laptop, Qty: 2, Unit Price: $1,200, Total: $2,400"` というプレーンテキストを抽出します。Markdownファイルの `#` 見出しや `**太字**` マーカーはプレーン文字として保持されます。

#### ステップ3: 分割（Split）

抽出したテキストを、より正確に取得しやすい小さな重複ありのチャンクに分割します。チャンクを小さくすることで、ドキュメント全体ではなく関連するセクションだけを返せるため、検索精度が向上します。チャンクサイズはコンテンツとアプリケーションによって異なります — 正確に取得できるほど集中していて、かつそれだけで意味をなすほど十分な大きさであることが目標です。

例：長いHR規定文書は、育児休暇のセクションが年次休暇のセクションとは別の独立したチャンクになるように分割されます。チャンクは文章が途中で切れないように、わずかに重複しています。

#### ステップ4: 埋め込みの作成（Create Embeddings）

各テキストチャンクを埋め込みに変換します — そのチャンクの*意味*を捉えた数値のリストです。意味が似ているチャンクは、使われている単語が異なっていても近い埋め込みを持ちます。

例：`"従業員は年間20日の有給休暇を受け取ります"` というチャンクは埋め込みに変換されます。ユーザーのクエリ `"休暇は何日もらえますか？"` は、単語がほぼ一致しなくてもこれに近い埋め込みを生成します。

> 埋め込みがLLM内部でどのように機能するか — テキストがどのように数値になり、意味がどのようにベクトル空間にエンコードされるか — については、[LLMは言語をどのように理解するか] をご覧ください。

#### ステップ5: 保存（Store）

各埋め込みをメタデータとともにベクトルストア（OpenSearch）に書き込みます。メタデータはコンテキストを保持し、エージェントが後でチャンクを取得したときにその出所を把握できるようにします。

例：各保存エントリには埋め込み、元のチャンクテキスト、および `{ "source": "company-benefits.md", "page": 2, "section": "年次休暇" }` のようなメタデータが含まれます。このメタデータは、元のソースドキュメントへの引用やリンクを表示するためにも使用できます。

検索品質は、ドキュメントの品質、チャンク戦略、埋め込みモデルの選択に大きく依存します。

---

### パート2: リトリーバル（検索・取得）

*ユーザーのクエリごとに実行されます。関連するコンテンツを見つけて回答を生成します。*

ユーザーが質問すると、エージェントはベクトルストアから最も関連性の高いチャンクを検索し、それを使ってグラウンドされた回答を生成します。

![リトリーバルパイプライン](cms:/Files/Images/appendix01-retrieval)

#### ステップ1: ユーザークエリ

ユーザーが自然言語で質問します。特別な構文やキーワードは不要です — チャットに入力するのと同じプレーンテキストです。

例：`"5年後の年次休暇は何日ですか？"` や `"第二養育者の育児休暇制度はどうなっていますか？"`

#### ステップ2: クエリの埋め込み（Embed Query）

インジェスション時に使用したのと全く同じモデルを使って、質問を埋め込みに変換します。これは非常に重要です — クエリの埋め込みと保存されたチャンクの埋め込みは、同じモデルで生成されなければ比較できません。

例：`"年次休暇は何日もらえますか？"` は、質問のキーワードだけでなく*意味*を捉えた埋め込みになります。

#### ステップ3: ベクトルストアの検索（Search Vector Store）

クエリの埋め込みを使って、ベクトルストアの中から最も類似した埋め込みを検索します。これは数学的な最近傍探索であり、異なる単語を使っていても質問の意味に最も近いチャンクを見つけます。

例：年次休暇に関するクエリが全ての保存済みチャンクの埋め込みと比較されます。`company-benefits.md` の「年次休暇」セクションのチャンクは、全てのチャンクに「年次休暇」という正確なフレーズが含まれていなくても、クエリの意味に近いため高いスコアを得ます。

#### ステップ4: 結果のランク付け（Rank Results）

一致した全チャンクが類似度スコアでランク付けされます。スコアが高いほど、そのチャンクがユーザーの質問により関連していることを示します。最小閾値（`AI.RAG.MinScore`）を下回るチャンクは除外されます。

例：検索が `チャンクA（スコア0.92）`、`チャンクB（スコア0.85）`、`チャンクC（スコア0.73）` を返し、閾値以下のチャンクは除外されます。

#### ステップ5: 上位K件の選択（Select Top-K）

スコアの高い上位Kチャンクが、LLMに渡すコンテキストとして選択されます。KはAI.RAG.MaxResults設定で制御されます。

例：`MaxResults: 3` の場合、20チャンクが最小スコアフィルターを通過していても、チャンクA・B・Cのみが選択されます。

#### ステップ6: コンテキストの提供（Provide Context）

選択されたチャンクが元の質問とともにLLMプロンプトに注入されます。LLMは取得されたコンテンツを読み、学習データからではなく、それらの特定の段落に基づいた回答を生成します。

例：LLMは `"5年後の年次休暇は何日ですか？"` という質問と、取得されたチャンク `"5年の勤続後、年次休暇は25日に増加します。"` を受け取り、正確で出典のある回答を返します。

#### なぜSQLを使わないのか？

この時点で自然な疑問が浮かびます：ドキュメントとそのテキストはただの文字列です — なぜリレーショナルデータベースに保存して `WHERE content LIKE '%年次休暇%'` のようにクエリしないのでしょうか？

問題はキーワードマッチングにあります。SQLは完全な文字列の一致を探します。*「休暇は何日もらえますか？」* と尋ねるユーザーは、*「年次休暇ポリシー」* というタイトルのチャンクの単語を一つも含んでいません。意味は同じでも、クエリは何も返しません。

ベクトル検索は異なる仕組みで動作します。クエリと保存されたチャンクの両方が埋め込みに変換されます — 意味を数値で表現したものです。検索は、使われている単語に関わらず、クエリに最も意味が近いチャンクを見つけます。

![SQL vs vector store](cms:/Files/Images/appendix01-sql-vs-vector)

---

> **注意：** RAGは取得されたドキュメントに基づいて回答を根拠づけることで事実の正確性を大幅に向上させますが、LLMは取得された情報を誤解釈する場合があります。ソースドキュメントの品質は引き続き重要です。

## まとめ

| | インジェスション | リトリーバル |
| --- | --- | --- |
| **実行タイミング** | ドキュメントが変更されたとき | ユーザーの質問ごと |
| **目的** | 検索のためにナレッジを準備する | 関連するナレッジを見つける |
| **主な入力** | ドキュメント | ユーザーのクエリ |
| **主な出力** | 検索可能な埋め込みインデックス | グラウンドされた回答 |
| **LLMを使用？** | 埋め込みモデルのみ | 埋め込みモデル＋生成LLM |

## 次のステップ

RAGパイプラインの基本を理解したら、次のトピックでさらに深く学べます。これらのトピックはこのチュートリアルでは扱っていません — 外部リソースを通じて各自で調べることをお勧めします。

- **チャンク戦略**: ドキュメントの分割方法が検索精度に影響します。コンテンツの種類によって適切な戦略（固定サイズ、再帰的、セマンティック）が異なります。
- **埋め込みモデル**: モデルの選択が意味の捉え方を決定します。言語サポート、ドメイン特化性、パフォーマンスによってモデルは異なります。
- **ベクトルデータベース**: 大規模な埋め込みの保存と検索に最適化された専用データベースです（例：OpenSearch、Pinecone、Weaviate）。
- **ハイブリッド検索**: セマンティック検索とキーワード検索を組み合わせ、製品コードや固有名詞などの完全一致が必要な語句に対する検索精度を向上させます。
- **再ランク付け（Re-ranking）**: より精度の高いモデルを使って取得済みチャンクを再スコアリングし、LLMに渡す前に精度を上げる二段階の処理です。
- **メタデータフィルタリング**: ベクトル検索の前後に、ドキュメントの属性（部署、日付範囲など）でフィルタリングして検索範囲を絞り込みます。

## まとめのポイント

- RAGはLLMを再学習することなく、自社のドキュメントを活用できるようにします。
- ドキュメントはインジェスション時に一度だけ準備されます。
- 全ての質問がリトリーバル検索を起動します。
- 最も関連性の高いドキュメントチャンクだけがLLMに送られます。
- より良いソースドキュメントが、より良い回答につながります。
