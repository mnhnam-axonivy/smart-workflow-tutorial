# LLMは言語をどのように理解するか

質問を入力してAIが知的に返答するとき、まるで機械が読んで考えているように見えます。しかし内部では、モデルは言葉を一切見ていません — 見ているのは数値だけです。この付録では、テキストを文脈的な表現に変換し、最終的に回答を生成する5つのステップを説明します：

1. テキストをトークンに分割する。
2. トークンを数値（トークンID）に変換する。
3. その数値を意味を表す埋め込みに変換する。
4. セルフアテンションを使って意味を文脈に基づいて更新する。
5. 次のトークンを予測して回答を生成する。

## 身近な例：楽譜を読む

音楽家は楽譜を見たとき、音楽を「聴く」わけではありません — ページ上の記号を見ています。各記号には名前があり、五線譜上の位置があり、長さがあります。音楽家はその記号を指の動きに変換し、音を生み出し、聴衆はそれをメロディーとして聴きます。

LLMも言語に対して同様のことをします：

| 楽譜 | LLMの処理 |
| --- | --- |
| ページ上の音符 | テキスト入力 |
| 各音符の名前を付ける（C、D、E…） | トークン化 |
| 各音符に位置番号を割り当てる | トークンID変換 |
| 同じ音符が長調と短調で異なる響きを持つことを知る | 埋め込み — 各トークンの初期的な意味 |
| 曲全体の文脈でフレーズを解釈する | セルフアテンション — 文脈に基づく更新 |
| メロディーを演奏する | 回答の生成 |

音楽家は作曲家がどんな感情を持っていたかを理解する必要はありません。学習したルールに従って記号を処理し — そして結果は意味のあるものになります。LLMも同じように動作します。

## 核心的な問い

数値しか理解しないモデルが、どのように言語を理解するのでしょうか？答えは、テキストを豊かな数値表現に変換し、処理し、1トークンずつ回答を生成する5ステップのパイプラインです。

---

## ステップ1: トークン化（Tokenization）

まず最初に、入力テキストは**トークン**と呼ばれる小さな単位に分割されます。トークンは単語、単語の一部、または句読点になります。モデルは生の文字を処理することはなく、常にトークンで動作します。

例：`"unhappiness"` という単語は1つの単位として扱われません。WordPiece記法を使うトークナイザーは `["un", "##happiness"]` に分割します。`##` プレフィックスは「このピースは前のトークンにスペースなしで続く」ことを意味します。

異なるトークナイザーは異なる規則を使います：
- **WordPiece**（BERT）: 続きのピースに `##` を付与 → `["un", "##happiness"]`
- **SentencePiece**（LLaMA、Gemini）: 単語の先頭に `▁` を付与 → `["▁un", "happiness"]`

なぜ単語を分割するのでしょうか？固定語彙はあらゆる言語のすべての単語を収録できないからです。サブワードへの分割により、モデルは既知のピースを組み合わせることで、稀な単語、誤字、新しい用語を扱えるようになります。

## ステップ2: トークンID変換（Token ID Conversion）

各トークンは、モデルの語彙辞書を参照して**トークンID**と呼ばれる一意の整数にマッピングされます。語彙はトレーニング時に固定され、数万のエントリを含みます。

例：`"What is the weather?"` という文は次のようにトークン化・変換されます（値はあくまで例示です — 実際のIDはモデルの語彙によって異なります）：

| トークン | トークンID |
| --- | --- |
| `What` | 3195 |
| `is` | 278 |
| `the` | 370 |
| `weather` | 15079 |
| `?` | 28804 |

モデルは `[3195, 278, 370, 15079, 28804]` という配列を保持します。内部的に、モデルは数値表現のみで動作します。元のテキストはもう直接処理されません。

---

## ステップ3: 埋め込みの検索（Embedding Lookup）

トークンIDは整数ですが、整数だけでは意味を持ちません — `3195` はモデルに「What」が何を意味するか、他の単語とどう関連するかを何も伝えません。次のステップでは、各トークンIDを**埋め込み**と呼ばれる高密度ベクトルに変換します。

各トークンIDは、大きなベクトルテーブルから学習済み埋め込みを検索するために使われます。これらの埋め込みはトレーニング中に学習され、モデルが言語を学ぶにつれて更新されました — 入力のたびに新しく計算されるわけではありません。各埋め込みは数百から数千の浮動小数点数のリストで、各数値は学習されたセマンティック空間の1次元を表します。意味が似ているトークンは近いベクトルを持ちます — その空間で互いに近い位置にあります。

例：Word2Vec（2013年）からのセマンティック空間の古典的な例：

```
vector("king") - vector("man") + vector("woman") ≈ vector("queen")
```

この有名な例は、ベクトル空間でどのように意味の関係が生まれるかを示しています — 「king」と「queen」は王族の次元で近く、「man」と「woman」は性別の次元で異なります。現代のトランスフォーマーモデルは異なる埋め込みアーキテクチャを使いますが、この直感は今でも有用です。

![Embedding vector space](cms:/Files/Images/appendix02-embedding-space)

> **注意：** この例はWord2Vecという古い静的埋め込みモデルのものです。現代のLLMでは、このステップでのトークン埋め込みはまだ文脈を考慮しません — `"bank"` という単語は `"river bank"` に現れても `"savings bank"` に現れても同じ初期ベクトルを持ちます。その文脈感度はステップ4のセルフアテンションで追加されます。

### RAGの埋め込みについての補足

上記で説明した埋め込みは、LLMのトレーニング中に学習された*内部的な*トークンレベルの表現です。RAGは別の種類の埋め込みを使います — 専用の埋め込みモデル（例えば `text-embedding-3-small`）によって生成される*文レベルの*埋め込みです。そのモデルは文章や段落全体を1つのベクトルにエンコードし、それがOpenSearchに保存されて検索時に比較されます。

基本的な原理は同じです — 意味はベクトル空間の位置としてエンコードされます — ただし、これらは異なる目的を持つ異なるモデルです。`"休暇は何日もらえますか？"` を検索する場合、RAG埋め込みモデルはクエリ全体を1つのベクトルに変換し、最も近い保存済みチャンクベクトルを見つけます。これはLLMが回答を生成する際に内部で使うトークン埋め込みとは異なります。

## ステップ4: 文脈に基づく更新（セルフアテンション）

生の埋め込みは単独でのトークンの意味を捉えます。しかし多くの単語は文脈によって異なる意味を持ちます。セルフアテンションが始まる前に、モデルは各トークンに位置情報も追加し、シーケンスの順序を把握します — これがないと `"dog bites man"` と `"man bites dog"` は同じように見えてしまいます。

**セルフアテンション**は、同じシーケンスの他のトークンに基づいて各トークンの埋め込みを更新するメカニズムです。どの単語が互いに最も重要かを決定するために、トランスフォーマーはすべてのトークンを他のすべてのトークンと比較します。これはQuery（クエリ）、Key（キー）、Value（バリュー）という3つの学習済みベクトルを使って行われます。各トークンについて、モデルはこれら3つのベクトルを生成します：

| ベクトル | 役割 |
| --- | --- |
| **Query（Q）** | 「私は何を探していますか？」 |
| **Key（K）** | 「私は何を含んでいますか？」 |
| **Value（V）** | 「選択された場合、私はどんな情報を提供しますか？」 |

2つのトークン間のアテンションスコアは、QとKベクトルの内積です。高いスコアは、この文脈で2つのトークンが強く関連していることを意味します。モデルはこれらのスコアを使ってValueベクトルをブレンドし、文全体の文脈を反映するように各トークンの表現を更新します。

例：`"I deposited money at the bank"` では、`"bank"` は金融機関を意味するべきです。`"We sat on the river bank"` では、同じ単語が川岸を意味するべきです。セルフアテンションは周囲のトークンを使って、それぞれの場合で `"bank"` の埋め込みを異なる方法で更新します。

これにより、すべての単語が周囲の単語に応じてその意味を変えることができます — これがLLMを言語処理において非常に効果的にする核心的な機能です。

## ステップ5: 次のトークンの予測（Predict the Next Token）

セルフアテンションがトークンの表現を更新した後、モデルは最も可能性の高い次のトークンを予測します。その新しいトークンがシーケンスに追加され、プロセス全体が繰り返されます — モデルは回答が完成するまで1トークンずつ回答を生成します。

---

## LLMが実際に行っていること

正確に理解することが重要です：**LLMは人間のように言語を理解しているわけではありません。** 現代のLLMには人間のような理解、意図、意識はありません。代わりに、トレーニング中に学習した統計的パターンを認識することで回答を生成します。理解しているように見えるものは、トークンとその文脈の間の数十億の学習済み数値関係の結果です。

重要な洞察：ステップ3で導入された埋め込みは単なる出発点です。すべてのトランスフォーマー層がこれらの表現を更新し、ベクトルは最終層までに非常に豊かな文脈情報をエンコードするまで継続的に変化します。

![LLM layer stack](cms:/Files/Images/appendix02-layer-stack)

これには実際的な意味があります：

- パターンが一致しても事実が一致しない場合、モデルは自信を持って間違える可能性があります
- トレーニングデータになかったことは知ることができません
- 異なる順序の同じ単語でも、まったく異なる出力が生成される場合があります

これがまさにRAGが存在する理由です：事実に関する質問についてモデルの学習パターンに頼るのではなく、RAGは実際のソーステキストを取得し、モデルの生成をそれに基づいて行います。

## まとめ

| ステップ | 目的 |
| --- | --- |
| **トークン化** | テキストを扱いやすいピースに分割する |
| **トークンID** | 各ピースを語彙番号にマッピングする |
| **埋め込み** | 各トークンの初期的な意味を表現する |
| **セルフアテンション** | 周囲の文脈に基づいて意味を更新する |
| **次のトークン予測** | 1トークンずつ回答を生成する |

私たちはLLMと言葉を使ってやり取りしますが、モデル内部のすべての段階 — プロンプトの理解から回答の生成まで — は完全に数値を使って行われます。

LLMが内部でテキストをどのように処理するかを理解したことで、RAGが関連するドキュメントチャンクを追加コンテキストとして提供する理由がよりよく分かるでしょう — モデルはそれらのチャンクをトークンシーケンスの一部として受け取り、まさにこのパイプラインで処理します。
