# 会話メモリ

デフォルトでは、各`AgenticProcessCall`はステートレスです — 1つのメッセージを処理し、すべてを忘れます。**会話メモリ**は、エージェントが各ターンで会話履歴全体にアクセスできるようにし、一貫したマルチターン対話を可能にします。

---

> **実際の動作を確認するには：** フィーチャー13（[ヒューマンインザループ]）は`aiMemoryId`をパターンの必須要素として使用しています — 請求書承認エージェントがタスクの途中で一時停止し、人間が書面による理由を入力した後に再開します。そのプロセスが`aiMemoryId`の最も良い実例です。`tutorial/processes/tutorial/features/Feature13.p.json`を参照してください。
>
> ![フィーチャー12 データクラス](cms:/Files/Images/feature12-00)

---

## 始める前に

ステートレスなエージェントは各質問を独立して回答します。ユーザーが「あの価格はいくらでしたか？」や「前の回答を改善できますか？」と尋ねても、ステートレスエージェントは応答できません — 以前のやり取りの記録がないからです。会話メモリは、完全なメッセージ履歴を保存し、後続のすべてのLLM呼び出しに注入することでこの問題を解決します。

---

## 仕組み

プロセスデータクラスに**`aiMemoryId`**（型：`String`）という名前のフィールドを追加します。フレームワークはこのフィールドを名前で認識し、自動的に次の処理を行います：

1. 最初のエージェント呼び出し時に会話の一意のメモリIDを生成
2. IDを`in.aiMemoryId`に書き込む
3. 後続の各呼び出し前に`in.aiMemoryId`を読み取る
4. 保存されたメッセージ履歴を読み込み、LLMリクエストの先頭に追加

3種類のストレージバックエンドが利用可能です：

| メモリタイプ | ストレージ | 用途 |
| --- | --- | --- |
| `IvyVolatileStore` | JVMメモリ | デフォルト — 開発またはシングルサーバー |
| `IvyMemory` | Ivyケース/プロセスデータ | プロセス範囲の会話 |
| `BusinessDataMemory` | Ivy Business Data（DB） | 本番 — 再起動後も持続、クロスセッション |

---

## なぜ使うのか？

- **マルチターン対話** — ユーザーが以前のメッセージを参照できる（「あの価格はいくらでしたか？」）
- **文脈を考慮したフォローアップ** — エージェントが以前の回答を改善、要約、または詳述できる
- **ウィザード形式のフロー** — アクションを起こす前に複数のターンで情報を収集する
- **コード不要** — Java実装は不要、`aiMemoryId`フィールドだけでよい

---

## ステップ1 — データクラスにaiMemoryIdを追加する

プロセスデータクラスに`aiMemoryId`という名前の`String`フィールドを追加します：

```json
{ "name": "aiMemoryId", "type": "String" }
```

> フィールド名は**フレームワークの規約**です。正確に`aiMemoryId`とスペルする必要があります。異なる名前のフィールドはフレームワークに認識されません。

---

## ステップ2 — エージェントを実行する

`AgenticProcessCall`要素への変更は不要です。データクラスに`aiMemoryId`が存在すれば、メモリは完全に自動です。

**最初のプロセスインスタンス：** メモリIDが生成され、`in.aiMemoryId`に書き込まれます。やり取り（ユーザーメッセージとエージェントの返信）がそのIDで保存されます。

**次のプロセスインスタンス**（例：ユーザーがフォローアップメッセージを送信）：前のインスタンスから同じ`in.aiMemoryId`を引き継ぎます。フレームワークは保存された履歴を読み込み、LLMリクエストの先頭に追加します — エージェントは会話全体を記憶しています。

> 会話のすべてのターンで`in.aiMemoryId`を安定させてください。呼び出し間でリセットや再生成をしないでください — それは新しい空の会話を開始することになります。

---

## プロセスインスタンス間でのメモリの仕組み

[ヒューマンインザループ]の請求書承認プロセス（`Feature13.p.json`）が最も分かりやすい実例です。すべては**1つのプロセスインスタンス**の中で起こります — `aiMemoryId`がサスペンド中のエージェントの状態を保持するスレッドです：

```text
1. プロセス開始 — in.aiMemoryId = ""（空）

2. エージェントが初回実行
   → フレームワークがメモリIDを生成して書き込み: in.aiMemoryId = "mem-8f3a2c"
   → エージェントが請求書 INV-2025-0892（$12,500）を受け取る
   → 金額が$2,000を超えると判断 — askUserFeedback を呼び出す
   → askUserFeedback が human:decision をスロー — エージェントの実行がサスペンド
   → in.aiMemoryId = "mem-8f3a2c" はプロセスデータに保持されたまま

3. タスクリストに「Provide feedback for Invoice Approval Agent」タスクが表示される
   → 人間がタスクを開き、入力：「承認済み — Q3インフラ予算で対応」
   → UserTask の出力コードが実行：
        new DecisionMaker("mem-8f3a2c").resolve("承認済み — Q3インフラ予算で対応")
   → 回答が "mem-8f3a2c" に保存されたサスペンド中の会話に書き込まれる

4. フローが同じ ProgramInterface 要素に戻る
   → in.aiMemoryId = "mem-8f3a2c" でエージェントが再開 — 会話履歴は完全に保持
   → サスペンドされた askUserFeedback ツール呼び出しが人間の回答を返す
   → エージェントが承認を確認して終了
   → in.result = "Invoice INV-2025-0892 approved. Reason: 承認済み — Q3インフラ予算で対応"

5. TaskSwitchEvent が正式な承認タスクを作成
   → 名前：「Invoice INV-2025-0892 Approval」
   → 説明：「Justification reason: 承認済み — Q3インフラ予算で対応」
```

`aiMemoryId`がなければ、ステップ4では全く新しい空の会話が開始されます — エージェントは処理中だった請求書の記録を持たず、`DecisionMaker.resolve()`は書き込み先のメモリストアを持ちません。

---

## 設定リファレンス

| フィールド | 説明 |
| --- | --- |
| `aiMemoryId`（データクラスフィールド） | 会話スレッドを識別する一意の文字列。最初の呼び出し時に自動生成されます。履歴を維持するために後続のすべてのリクエストで引き継いでください。 |

---

## よくある間違い

- **ターン間でメモリIDをリセットする** — プロセスインスタンス間で`in.aiMemoryId`がクリアまたはリセットされると、各ターンは空の履歴で開始され、エージェントはコンテキストを持ちません。
- **メモリの無制限な増加** — 会話履歴はすべてのLLM呼び出しの先頭に追加されます。長い会話は消費トークン数が増え続けます。非常に長いセッションでは履歴の要約を検討してください。
- **本番環境での`IvyVolatileStore`の使用** — デフォルトのVolatileストアはJVMメモリ内にのみ存在します。サーバーの再起動やクラスターフェイルオーバーですべての会話が消去されます。本番のマルチターンチャットには`BusinessDataMemory`を使用してください。
