# エージェントパターン: エージェントパイプライン

エージェントパイプラインは、エージェントを直線的につないだものです。各エージェントは1つの明確な仕事だけを行い、その結果を次のエージェントに渡します。タスクに複数の種類の思考（ドキュメントを読む、分析する、判断する）が必要になったら、すべてを1つの大きなエージェントに任せるよりも、複数の小さなエージェントに分割するほうが、ほぼ常に良い結果になります。

---

> **ベストプラクティスの例:** `best-practices/process/exercise/purchasing/` の購買演習は、3段階のパイプラインです。
>
> 1. **Read Document**（`agents/DocumentReader.p.json`） — ビジョン対応のエージェントが、アップロードされた購買ドキュメントをテキストに変換します
> 2. **Purchasing Manager Agent**（`agents/PurchasingAgent.p.json`） — そのテキストをツールで処理し、型付きの `PurchasingData` オブジェクトを返します
> 3. **Decide Approval**（`Purchasing.p.json`） — `PurchasingData` を読み取り、型付きの `ApprovalRecord` を返します
>
> 最小の例はチュートリアル自体にあります。`Feature03.p.json` は *Invoice Analysis → Urgency Classifier → Supplier Risk Check* をつないでいます。[モデルプロバイダーの選択] を参照してください。

## 使用する場面

作業が**順序の決まったステップに分解でき、各ステップに異なる指示が必要な場合**（抽出 → 分類 → 要約など）にパイプラインを使用します。各ステップは短い専用のシステムメッセージを持ち、確認可能な結果を生成します。

パイプラインを作ること自体を目的にしないでください。明確なシステムメッセージを持つ1つのエージェントで確実に処理できるなら、2つ目のエージェントはコストとレイテンシを増やすだけです。また、ステップの*順序*が決まっておらず、次に何をするかをモデルに判断させたい場合は、1つのエージェントに複数のツールを与えてください（[呼び出し可能プロセスツール]）。

---

## 仕組み

各ステージは通常の `AgenticProcessCall` です。ステージ同士は、共有された会話ではなく**プロセスデータ**でつながります。エージェントは前のエージェントのことを何も覚えていないため（[会話メモリ] を参照）、ステージが必要とする情報はすべてユーザーメッセージに含める必要があります。

```text
uploaded document
      │
      ▼
┌──────────────────┐    extractedText     ┌──────────────────────────┐   PurchasingData  ┌──────────────────┐
│  Read Document   │ ───────────────────▶ │ Purchasing Manager Agent │ ────────────────▶ │ Decide Approval  │
│  vision model    │                      │ tools + typed result     │                   │ typed decision   │
└──────────────────┘                      └──────────────────────────┘                   └──────────────────┘
```

ステージをつなぐ要素は3つあります。

- **結果のマッピング先** が、あるステージの結果をプロセスデータのフィールドに書き込みます。
- **期待する結果の型** が、その結果を型付きオブジェクトにします。次のステージやゲートウェイは、テキストをパースする代わりに個々のフィールドを読み取れます（[構造化出力]）。
- 次のステージの**ユーザーメッセージ**が、`<%=...%>` でそのフィールドを参照します。

---

## 得られるもの

- **可視性** — 各ステージが独自の会話記録とトレースを持つため、1つの長いやり取りを読む代わりに、各ステージが何を受け取り、何を返したかを確認できます（[観測可能性]）。
- **ステージごとに最適なモデル** — ドキュメントの読み取りにはビジョンモデル、難しい判断には高性能モデル、単純な分類には安価なモデルを使用できます（[モデルプロバイダーの選択]）。
- **ステージごとのガードレール** — 各エージェントが、そのステージに本当に必要な検証だけを行います。
- **障害の分離** — ガードレール違反や [サーキットブレーカー] による停止は、1つの要素にだけ影響します。前のステージの結果をプロセスデータに残したまま、そのステージだけをフォールバックにルーティングできます。

## ベストプラクティス: ステージ間では型付きオブジェクトを渡す

ステージ間でフリーテキストを渡すと、次のエージェントが文章をもう一度解釈しなければならず、値が存在するかどうかも検証されません。各ステージにデータクラスを返させ、それを次に渡します。

| ステージ | 期待する結果の型 | 次のステージが読み取るもの |
| --- | --- | --- |
| Purchasing Manager Agent | `exercise.purchasing.PurchasingData.class` | `title`、`department`、`totalAmount`、`lineItems` など |
| Decide Approval | `exercise.common.ApprovalRecord.class` | `isApproved` と `approvalNote` — [プラクティス 01 — エージェントパターン: AIタスク] を参照 |

型付きの結果があれば、AIが不要な箇所を**プロセス**に任せることもできます。`Purchasing.p.json` では、ゲートウェイ *Total > 100,000?* が数値で判定しており、モデルには尋ねていません。

## ベストプラクティス: 1ステージに1つの仕事

各ステージのシステムメッセージには、そのステージのことだけを書きます。読み取り担当が承認ルールを知る必要はなく、承認担当がスキャンの読み方を知る必要もありません。あるステージに「ついでにこれも」という指示が増えてきたら、ステージを追加する時期です。

各ステージには、必要なツールだけを与えます。付与したツールはすべて、リクエストのたびにトークンを消費し、モデルが誤った選択をする余地を増やします。

## ベストプラクティス: すべてのステージにフォールバックを用意する

どのステージも、ガードレール、[サーキットブレーカー]、プロバイダーの障害によって停止する可能性があります。各エージェントにエラー境界イベントをアタッチし、そのときプロセスが何をするか（後でリトライする、担当者に引き継ぐ、AIを使わないルートで続行する）を決めてください。ステージが呼び出し可能サブプロセスの中にある場合は、[プラクティス 02 — エージェントパターン: サブプロセス設計とツールの同一配置] で説明しているように、内部でエラーをキャッチしてフラグを返します。

## よくある間違い

- **後続のエージェントが前のエージェントを覚えていると期待する** — エージェント呼び出しの間では何も引き継がれません。データはユーザーメッセージで渡してください。
- **型付きオブジェクトではなく文章を渡す** — 次のステージが推測することになり、値の欠落にも気づけません。
- **早すぎる分割** — 1つで済む処理を2つのエージェントに分けると、コストとレイテンシが2倍になります。
- **パイプライン全体に1つのフォールバック** — ステージ3の失敗で、ステージ1と2の結果まで捨てるべきではありません。
- **ゲートウェイで判定できることをモデルに判断させる** — 2つの数値の比較は、プロンプトではなくプロセスの仕事です。
